# Mining targets and balance views (BTC, XMR, PRL)

The site mining overview links to **Mining targets**. This view keeps three concepts separate:

- A **pool account** is a provider API connection. Braiins supplies BTC balance, worker count and suggested worker prefix. XMR/PRL Kryptex target balances use the public payout-address API already used by the PC agent; other XMR/PRL pools show no balance. The view lists BTC ASICs by their saved target and XMR/PRL agents by the configurations reported by each agent. Neither assignment nor a pool API worker count proves an accepted share.
- A **mining target** stores a canonical mining coin (`bitcoin`, `monero`, `pearl`), its algorithm, payout coin, Stratum URL, worker prefix and priority. XMR/PRL also store a public payout address. SHA-256 BTC targets are applied to BraiinsOS and stock Antminer ASICs. RandomX/XMR and PearlHash/PRL targets are sent through coin-specific Core commands to each PC agent. The node appends an eight-character miner-ID suffix to the worker prefix, preserves the agent's Pearl GPU selection, and checks the agent's saved configuration before showing an assignment. A target is not proof of live mining.
- A **watched wallet** is a read-only public address tagged with its chain. BTC address balances come from [mempool.space's address API](https://mempool.space/docs/api/rest); PRL on-chain balance comes from the `pearlchain.live` explorer endpoint already used by the PC agent. A Monero public address cannot reveal its balance, so it is shown as unavailable. One BTC address does not represent an entire multi-address wallet. The Phoenixd-backed Lightning wallet remains BTC-only. The global header shows the Lightning balance, every watched wallet and every available pool balance as separate coin chips; it never adds quantities across coins.

For eligible ASICs and PC agents, lower priority numbers are tried first when applying a configuration. If Core or the agent rejects a target, the next enabled target is attempted. An already configured fallback is kept during scheduled reconciliation; the operator can explicitly reapply the list. With no active Node target for XMR or PRL, the agent's local configuration remains usable. With an active target, the Node reapplies its configuration if the agent reports a different route. Updating a route can stop its running worker; starting and dispatching mining still follow the existing agent and Node controls. There is **no automatic detection of a pool outage during ongoing mining**. Neither a saved target nor a pool API worker count proves a credited share. Use miner telemetry and the pool's own accounting to verify operation.

The generic Core pool-target contract remains limited to single-algorithm ASICs; the XMR and PRL agent commands configure the CPU and GPU routes independently. Unsupported ASIC operating systems remain manually configured. The mining overview and target page show agent workers under their reported algorithm. This change adds no new Stratum format, fee target or payout contract. Weighted distribution is not implemented. The finance view reads Kryptex's 31-day XMR/PRL reward chart and its price chart for configured Kryptex targets, stores daily rewards and shows the coin amounts alongside their historical fiat value. Current pool balances, on-chain wallet holdings and Lightning funds remain holdings and are never counted as mining income. Days without a reported target history or price are marked incomplete rather than estimated. The existing BTC sale FIFO ledger remains BTC-only.

API routes: `GET /api/pv-site/{siteId}/mining/coins`, `GET/POST /api/pv-site/{siteId}/mining/targets`, `GET /api/pv-site/{siteId}/mining/targets/assignments`, `DELETE /api/pv-site/{siteId}/mining/targets/{targetId}`, `POST /api/pv-site/{siteId}/mining/targets/apply?coin=...`, `GET /api/pv-site/{siteId}/mining/pools/overview`, and `GET/POST/DELETE /api/pv-site/{siteId}/watched-wallets`. Core exposes `/api/miners/monero/configuration` and `/api/miners/agent/coin-configurations` for Node reconciliation; both delegate to the PC agent's existing coin-specific configuration and overview APIs. Flyway migration `V12` creates the tables; `V13` tags existing targets and watched BTC addresses as Bitcoin and adds coin/payout fields; `V14` makes watched addresses unique per site and coin; `V15` persists the Kryptex daily reward history. Priority uniqueness is per coin.

## Integration-guide scope

This pass extends Node configuration and balance views for two existing mining coins and adds Node-to-agent target reconciliation; it does not introduce a new mining protocol or fee route. Existing XMR and PRL device/proxy/fee/portal paths remain as documented in the Pearl integration record. The coin guide's proxy, fee-backend, device OS, portal provisioning, calculator and rollout steps do not apply to these Node view/API changes because those contracts are unchanged. No live share or fee-credit verification was performed here. Automatic assignment is configuration reconciliation, not tested pool failover. Pool accounting outside Braiins and Kryptex needs a provider adapter; missing values remain unavailable.
